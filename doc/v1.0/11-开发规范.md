# 一、规范目标

本规范用于统一 HairHub V1.0 的开发方式、代码结构、命名规则和 AI 辅助编码原则。

主要目标：

* 保持项目结构简单
* 遵循 Laravel 传统开发习惯
* 降低个人开发维护成本
* 避免过度设计
* 保证 Cursor 生成代码风格一致
* 方便未来增加开发人员
* 为 V1.1、V2.0 持续迭代提供稳定基础

HairHub V1.0 的核心开发原则：

> Laravel 原生优先，简单优先，业务清晰优先，不为了架构而架构。

# 三、总体开发原则

## 3.1 简单优先

能够用 Laravel 原生能力解决的问题，不引入额外复杂框架。

优先使用：

```text
Eloquent ORM

Form Request

Service

Laravel Cache

Laravel Queue

Laravel Scheduler

Laravel Storage
```

避免无明确需求时引入：

```text
DDD

CQRS

Event Sourcing

微服务

复杂Repository体系

复杂领域模型

过度抽象
```

---

## 3.2 不为未来假设过度开发

允许数据库进行合理预留。

但不提前开发：

```text
用户系统

会员系统

订单系统

商城系统

支付系统

复杂权限

多语言完整业务

AI计费系统
```

原则：

> 可以为未来留门，但不要提前装修未来的房间。

---

## 3.3 一个问题只保留一种主要解决方式

例如：

图片统一由：

```text
MediaService
```

处理。

AI统一由：

```text
AiService
```

调用。

微信公众号统一由：

```text
WechatService
```

处理。

不要同时存在：

```text
Controller直接调用

Helper调用

Service调用

Model调用
```

多套实现方式。

---

## 3.4 优先遵循现有项目结构

Cursor 或开发人员修改代码前，必须先检查现有项目结构。

不得因为个人偏好随意：

* 重命名现有目录
* 移动大量文件
* 替换已有框架
* 修改无关模块
* 引入新的架构模式

原则：

> 先理解现有项目，再修改现有项目。

统一放在：

```text

```

例如：


```text

app/Domain/Hairstyle/Models/Hairstyle.php
```

原因：

V1.0 Model 数量有限，Laravel 标准目录更容易理解和维护。

---

## 4.2 API Controller

统一放在：

```text
app/Http/Controllers/Api/V1/
```

例如：

```text

VideoController.php
```

## 4.3 Dcat Admin Controller


例如：

不要为了目录完整而创建空类。

# 五、Controller 规范

## 5.1 Controller 职责

Controller 主要负责：

```text
接收请求

↓

参数验证

↓

调用业务逻辑

↓

返回响应
```

Controller 不应承担：

```text
复杂AI调用

复杂图片处理

复杂微信公众号同步

大量业务判断

长事务
```

---

## 5.2 简单查询允许直接使用 Model

例如：

```php
public function index()
{
    $items = Hairstyle::query()
        ->where('status', 1)
        ->paginate(20);

    return $this->success($items);
}
```

这种简单查询不需要强制创建：

```text
HairstyleService

HairstyleRepository

HairstyleQueryService
```

---

## 5.3 复杂业务进入 Service

例如 AI 生成：

```php
public function generate(AiGenerateRequest $request, AiService $aiService)
{
    $task = $aiService->generate(
        $request->validated()
    );

    return $this->success($task);
}
```

Controller 不直接：

```text
保存图片

创建任务

请求HairFastGAN

处理返回结果

保存AI结果

修改任务状态
```

这些属于 Service。

---

## 5.4 Controller 不允许过长

如果单个 Controller 方法出现：

```text
大量if/else

大量数据库操作

第三方API调用

图片处理

事务

超过明显合理长度
```

应考虑提取 Service。

不强制以具体代码行数作为唯一判断标准。

重点看职责是否清晰。

---

```text

微信公众号同步

复杂SEO生成

复杂内容发布流程

多个Model协作

数据库事务

外部API调用
```

---

## 6.2 Service 命名

使用：

```text
MediaService

AiService

WechatService

SeoService
```

避免模糊命名：

```text
CommonService

UtilsService

BaseBusinessService

ManagerService
```

---

## 6.3 Service 方法命名

推荐：

```php
upload()

generateThumbnail()

createTask()

generate()

syncArticle()

publishArticle()

cleanupExpiredMedia()
```

方法名称应表达业务动作。

---

## 6.4 Service 不应成为万能类

例如不要让：

```text
AiService
```

同时处理：

```text
图片上传

文章发布

SEO

微信同步
```

每个 Service 保持明确职责。

# 七、Repository 规范

## 7.1 V1.0 不强制 Repository

HairHub V1.0 不采用：

```text
每个Model

↓

一个Repository

↓

一个Interface

↓

一个Implementation
```

这种强制结构。

---

## 7.2 什么时候使用 Repository

只有出现以下情况时考虑：

```text
复杂查询大量重复

多个Service共享查询逻辑

未来可能替换数据源

单个Model查询逻辑非常复杂
```

---

## 7.3 简单 CRUD

直接使用：

```php
Hairstyle::query()
```

即可。

原则：

> Repository 是解决实际问题的工具，不是项目必须存在的形式。

# 八、Model 规范

## 8.1 Model 命名

使用单数 PascalCase：

```text
Hairstyle

HairstyleCategory

HairstyleTag

HairColor

Article

MediaFile

AiTask
```

---

## 8.2 表名

数据库表使用复数 snake_case：

```text
hairstyles

hairstyle_categories

hairstyle_tags

hair_colors

media_files

ai_tasks
```

---

## 8.3 Fillable

明确配置允许批量赋值字段。

例如：

```php
protected $fillable = [
    'name',
    'slug',
    'category_id',
    'description',
    'status',
    'sort',
];
```

不建议无理由使用：

```php
protected $guarded = [];
```

---

## 8.4 Casts

JSON、布尔值、日期等使用 casts。

例如：

```php
protected $casts = [
    'request_params' => 'array',
    'publish_time' => 'datetime',
    'status' => 'integer',
];
```

---

## 8.5 Model 关系

关系方法使用语义明确的 camelCase：

```php
public function category()

public function tags()

public function coverMedia()

public function wechatArticles()
```

---

## 8.6 Model 不承担外部 API 调用

禁止：

```php
$hairstyle->callHairFastGan();
```

外部 API 应由 Service 或 Provider 处理。

## 9.1 表名

统一：

```text
snake_case

复数
```

---

## 9.2 字段名

统一：

```text
snake_case
```

例如：

```text
category_id

cover_media_id

publish_time

created_at
```

---

## 9.3 主键

默认：

```text
id
```

类型：

```text
BIGINT UNSIGNED
```

Laravel Migration：

```php
$table->id();
```

---

## 9.4 外键字段

命名：

```text
{model}_id
```

例如：

```text
category_id

article_id

hairstyle_id

input_media_id
```

---

## 9.5 状态字段

简单启用状态：

```text
status
```

建议：

```text
0 = disabled

1 = enabled
```

复杂业务状态可以使用字符串或明确枚举值。

例如 AI 任务：

```text
pending

processing

success

failed
```

---

## 9.6 排序字段

统一：

```text
sort
```

建议：

```text
数值越小越靠前
```

全项目保持一致。

---

## 9.7 时间字段

默认：

```text
created_at

updated_at
```

需要软删除时：

```text
deleted_at
```

---

## 9.8 JSON 字段

适合保存：

```text
AI请求参数

灵活配置

未来扩展参数
```

不适合把需要频繁筛选、排序、关联的重要业务字段全部塞入 JSON。

原则：

> 需要查询的数据优先独立字段，灵活参数才使用 JSON。

---

## 9.9 索引

必须根据查询场景建立索引。

常见索引字段：

```text
slug

status

category_id

created_at

publish_time

task_no
```

唯一字段应增加唯一索引。

例如：

```text
slug

task_no
```

具体以业务唯一性为准。

# 十、Migration 规范

## 10.1 所有数据库结构通过 Migration 管理

禁止只在生产数据库中手工修改表结构而不提交 Migration。

---

## 10.2 Migration 必须可追踪

每次结构变化：

```text
创建Migration

↓

执行测试

↓

提交Git
```

---

## 10.3 已上线 Migration 不随意修改

开发阶段尚未部署时，可以合理调整。

正式上线后：

不要直接修改历史 Migration。

应该创建新的 Migration：

```text
add_xxx_to_hairstyles_table
```

---

## 10.4 字段注释

建议重要字段增加 comment。

例如：

```php
$table->tinyInteger('status')
    ->default(1)
    ->comment('状态：0禁用，1启用');
```

# 十二、异常处理规范

## 12.1 不吞异常

禁止：

```php
try {
    // ...
} catch (\Exception $e) {
}
```

异常必须：

```text
返回

记录

转换

或继续抛出
```

至少选择一种合理处理方式。

---

## 12.2 外部 API 异常

AI、微信等外部接口必须处理：

```text
连接失败

超时

HTTP错误

响应格式错误

业务失败
```

---

## 12.3 用户响应不暴露内部错误

前端：

```text
AI服务暂时不可用，请稍后重试。
```

日志：

```text
完整异常

Provider

任务编号

请求耗时

错误上下文
```

不要直接向用户返回：

```text
SQL语句

服务器路径

Stack Trace

API Secret
```

---

# 十三、日志规范

## 13.1 需要记录日志的场景

包括：

```text
AI调用失败

微信接口失败

文件上传失败

缩略图生成失败

定时任务失败

关键业务异常
```

---

## 13.2 日志必须有上下文

推荐：

```php
Log::error('HairFastGAN request failed', [
    'task_no' => $task->task_no,
    'provider' => 'hairfastgan',
    'error' => $e->getMessage(),

```

避免：

```php
Log::error('error');
```

---

## 13.3 禁止记录敏感数据

不要记录：

```text
AppSecret

API Key

Access Token

数据库密码

完整用户隐私数据
```

---

## 13.4 日志频道

V1.0 可以先使用 Laravel 默认日志。

如果实际日志量增加，再拆分：

```text
ai

wechat

media

application
```

不提前复杂化。

# 十四、事务规范

以下场景考虑事务：

```text
多个数据库写操作必须同时成功

创建主记录并创建关联数据

复杂内容发布流程
```

例如：

```php
DB::transaction(function () {
    // 保存主数据
    // 保存关联数据
});
```

---

## 14.1 不把外部 API 长时间调用包在数据库事务中

禁止：

```text
开启事务

↓

调用HairFastGAN等待30秒

↓

写数据库

↓

提交事务
```

这会导致事务长时间占用数据库连接和锁。

推荐：

```text
创建任务记录

↓

提交数据库事务

↓

调用AI API

↓

根据结果更新任务状态
```

这与你之前处理外部 API 拉取数据时采用的：

> 拉取数据无事务 + 保存数据有事务

原则一致。

# 十五、Media 开发规范

```text
MediaService
```

处理。

```text
↓

生成唯一文件名

↓

按年月日保存

↓

生成缩略图

↓

创建media_files

↓

返回MediaFile
```

---

## 15.2 路径规则

```text
storage/uploads/{source_type}/YYYY/MM/DD/
```

---

## 15.3 文件名

不要直接使用用户原始文件名作为物理文件名。

建议：

```text
UUID

随机字符串
```

原始文件名如有业务价值，可以单独保存。

---

## 15.4 用户上传图片

必须支持：

```text
expire_at
```

用于后续定时清理。

```text
docs/v1.0/12-AI设计.md
```

为准。

---

## 16.1 Controller 不直接调用模型 API

统一：

```text
Controller

↓

AiService

AI Provider

HairFastGAN API
```

```text
WechatService
```

必须存储在：

```text
.env
```

## 17.2 Access Token

应使用缓存。

---

## 17.3 同步必须记录结果

```text

微信Media ID

微信URL

同步状态

同步时间

错误信息
```

# 二十、队列规范

# 二十六、Cursor 使用规范

Cursor 是 HairHub 的主要 AI 辅助开发工具之一。

Cursor 可以：

```text
阅读项目文档

分析现有代码

生成Migration

生成Model

生成Dcat Admin CRUD

生成API

重构代码

编写测试
```

但 Cursor 不应在缺少项目上下文时自由决定核心架构。

---

## 26.1 Cursor 开发前必须阅读相关文档

例如开发发型模块：

```text
请先阅读：

docs/v1.0/01-项目定位.md
docs/v1.0/02-系统架构.md
docs/v1.0/03-模块设计.md
docs/v1.0/04-数据库设计.md
docs/v1.0/05-API设计规范.md
docs/v1.0/06-Dcat后台设计.md
docs/v1.0/08-开发任务拆解.md
docs/v1.0/11-开发规范.md
```

不需要每次读取所有文档。

根据任务选择相关文档。

---

## 26.2 Cursor 修改代码前先分析现有代码

要求：

```text
先检查现有目录

↓

找到相似实现

↓

理解项目习惯

↓

列出修改计划

↓

再开始编码
```

---

## 26.3 禁止 Cursor 随意修改架构

除非明确要求，否则不得：

```text
引入DDD

引入Repository全套架构

更换框架

移动大量目录

修改无关代码

批量重写已有功能

引入大量新依赖
```

---

## 26.4 每次只处理明确任务

推荐：

```text
实现 hairstyle_categories Migration
```

然后：

```text
实现 HairstyleCategory Model
```

然后：

```text
实现 Dcat Admin 发型分类管理
```

对于关联紧密的小任务，可以一次完成，但必须保持修改范围可控。

---

## 26.5 Cursor 完成后必须报告

要求 Cursor 输出：

```text
1. 完成内容

2. 修改文件

3. 新增文件

4. 数据库变化

5. 新增依赖

6. 测试方法

7. 尚未完成内容

8. 潜在风险
```

---

## 26.6 Cursor 不确定时不得猜测

如果发现：

```text
数据库设计与代码冲突

文档之间存在冲突

现有代码已有另一套实现

第三方API行为不明确
```

应该：

> 先说明冲突，再提出建议，不直接大范围修改。

# 三十二、总结

HairHub V1.0 的开发理念：

> 用 Laravel 原生、简单、清晰的方式解决真实业务问题。

核心原则：

```text
简单优先

Laravel原生优先

现有结构优先

业务清晰优先

不过度抽象

不过度开发

复杂业务使用Service

外部AI使用Provider

媒体统一管理

API统一响应

异常必须可追踪

数据库变更必须Migration

重要功能必须验证

Cursor必须先理解项目再修改代码
```

对于 HairHub 当前阶段：

> 最好的架构不是最复杂的架构，而是能够让一个人快速开发、稳定上线、持续运营，并且未来仍然容易扩展的架构。
