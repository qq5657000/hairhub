# HairHub V1.0 发型模块 MySQL 表结构详细设计

> Version: 1.0.0  
> 适用项目：HairHub 发型中心  
> 技术栈：Laravel 10 + Dcat Admin + MySQL 8.0+  
> 文档路径：`/docs/v1.0/database/01-发型模块.md`

---

# 一、模块目标

发型模块用于管理 HairHub 的核心发型资产，包括：

- 发型分类
- 发型资料
- 发型标签
- 发型与标签关系
- 发型封面及展示属性
- AI 换发型提示词
- SEO 基础信息

V1.0 涉及以下数据表：

```text
hairstyle_categories
hairstyles
hairstyle_tags
hairstyle_tag_relations
```

---

# 二、数据关系

```text
hairstyle_categories
        │
        │ 1:N
        ▼
    hairstyles
        │
        │ N:N
        ▼
hairstyle_tag_relations
        │
        │ N:1
        ▼
 hairstyle_tags
```

关系说明：

- 一个发型分类可以包含多个发型。
- 一个发型只能归属一个主分类。
- 一个发型可以拥有多个标签。
- 一个标签可以被多个发型使用。
- `hairstyle_tag_relations` 负责维护发型与标签的多对多关系。

# 三、统一设计约定

## 3.1 基础规范

- 存储引擎：`InnoDB`
- 字符集：`utf8mb4`
- 主键：`BIGINT UNSIGNED AUTO_INCREMENT`
- 不创建数据库物理外键
- 所有逻辑关联字段必须建立索引
- 状态字段使用 `TINYINT UNSIGNED`
- 状态值由 PHP Enum 统一管理
- 业务主表根据需要使用软删除
- 关联表不使用软删除

## 3.2 排序规则

后台默认排序：

```text
sort DESC, id DESC
```

说明：

- `sort` 越大，展示优先级越高。
- `id` 用于保证相同排序值下结果稳定。

## 3.3 状态规则

通用状态：

```text
0 = disabled
1 = enabled
```

对应 PHP Enum：

```php
enum CommonStatus: int
{
    case Disabled = 0;
    case Enabled = 1;
}
```

# 四、hairstyle_categories 发型分类表

## 4.1 表用途

管理发型分类，支持一级分类和二级分类。

示例：

```text
男生发型
├── 男生短发
├── 男生烫发
└── 男生长发

女生发型
├── 女生短发
├── 女生长发
└── 女生卷发
```

V1.0 建议只支持两级分类，数据库结构保留继续扩展的能力。

## 4.2 字段结构

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|---|---|---:|---:|---|
| id | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| parent_id | BIGINT UNSIGNED | 否 | 0 | 父分类 ID，0 表示顶级分类 |
| name | VARCHAR(100) | 否 | 无 | 分类名称 |
| name_en | VARCHAR(150) | 否 | `''` | 英文名称预留 |
| slug | VARCHAR(150) | 否 | 无 | SEO URL 标识 |
| description | VARCHAR(500) | 是 | NULL | 分类简介 |
| cover_media_id | BIGINT UNSIGNED | 否 | 0 | 分类封面媒体 ID |
| status | TINYINT UNSIGNED | 否 | 1 | 状态 |
| sort | INT UNSIGNED | 否 | 0 | 排序值 |
| created_at | TIMESTAMP | 是 | NULL | 创建时间 |
| updated_at | TIMESTAMP | 是 | NULL | 更新时间 |
| deleted_at | TIMESTAMP | 是 | NULL | 软删除时间 |

## 4.3 索引设计

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_slug` (`slug`),
KEY `idx_parent_status_sort` (`parent_id`, `status`, `sort`),
KEY `idx_cover_media_id` (`cover_media_id`),
KEY `idx_deleted_at` (`deleted_at`)
```

说明：

- `slug` 必须唯一。
- `parent_id + status + sort` 用于分类树和后台列表查询。
- `cover_media_id` 为媒体逻辑关联字段。
- 分类使用软删除。

## 4.4 建表 SQL 参考

```sql
CREATE TABLE `hairstyle_categories` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `parent_id` BIGINT UNSIGNED NOT NULL DEFAULT 0,
    `name` VARCHAR(100) NOT NULL,
    `name_en` VARCHAR(150) NOT NULL DEFAULT '',
    `slug` VARCHAR(150) NOT NULL,
    `description` VARCHAR(500) NULL,
    `cover_media_id` BIGINT UNSIGNED NOT NULL DEFAULT 0,
    `status` TINYINT UNSIGNED NOT NULL DEFAULT 1,
    `sort` INT UNSIGNED NOT NULL DEFAULT 0,
    `created_at` TIMESTAMP NULL DEFAULT NULL,
    `updated_at` TIMESTAMP NULL DEFAULT NULL,
    `deleted_at` TIMESTAMP NULL DEFAULT NULL,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_slug` (`slug`),
    KEY `idx_parent_status_sort` (`parent_id`, `status`, `sort`),
    KEY `idx_cover_media_id` (`cover_media_id`),
    KEY `idx_deleted_at` (`deleted_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 4.5 业务规则

- 顶级分类的 `parent_id = 0`。
- 不允许分类的父级指向自身。
- V1.0 不允许超过两级分类。
- 已被发型使用的分类不得直接物理删除。
- 删除分类前必须检查子分类和发型引用。
- `slug` 仅允许小写字母、数字和短横线。
- 分类名称允许重复，`slug` 不允许重复。

## 5.6 face_shape 和 suitable_scene 设计说明

V1.0 采用逗号分隔的枚举值，例如：

```text
face_shape = round,oval,square
suitable_scene = daily,work,date
```

原因：

- V1.0 数据量有限。
- 主要用于展示和轻量筛选。
- 可以减少过多关联表。
- 后续如需复杂推荐，可迁移为独立标签关系表。

约束：

- 只能保存系统定义的英文枚举值。
- 不允许直接保存中文展示名称。
- Laravel Model 应通过 Accessor 或 Cast 转为数组。
- 查询时不得大量依赖 `%LIKE%`，复杂推荐应改为关系表。

## 5.7 业务规则

- `category_id` 必须指向有效分类。
- 发型名称允许重复，`slug` 必须唯一。
- 上架状态下应存在有效封面。
- `published_at` 为空时视为未正式发布。
- AI Prompt 仅用于模型调用，不直接向前台用户展示。
- 删除发型时只软删除发型记录。
- 删除发型时同步删除标签关联记录。
- 不自动删除封面媒体文件。
- SEO 标题为空时可回退为发型名称。

# 七、hairstyle_tag_relations 发型标签关联表

## 7.1 表用途

维护发型和标签之间的多对多关系。

## 7.2 字段结构

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|---|---|---:|---:|---|
| id | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| hairstyle_id | BIGINT UNSIGNED | 否 | 无 | 发型 ID |
| tag_id | BIGINT UNSIGNED | 否 | 无 | 标签 ID |
| created_at | TIMESTAMP | 是 | NULL | 创建时间 |

说明：

- 关联表不需要 `updated_at`。
- 关联关系不存在修改概念，只有新增或删除。

## 7.3 索引设计

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_hairstyle_tag` (`hairstyle_id`, `tag_id`),
KEY `idx_tag_hairstyle` (`tag_id`, `hairstyle_id`)
```

说明：

- 唯一索引防止重复关联。
- 反向索引用于按标签查询发型。

## 7.4 建表 SQL 参考

```sql
CREATE TABLE `hairstyle_tag_relations` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `hairstyle_id` BIGINT UNSIGNED NOT NULL,
    `tag_id` BIGINT UNSIGNED NOT NULL,
    `created_at` TIMESTAMP NULL DEFAULT NULL,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_hairstyle_tag` (`hairstyle_id`, `tag_id`),
    KEY `idx_tag_hairstyle` (`tag_id`, `hairstyle_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

## 7.5 业务规则

- 不创建数据库物理外键。
- 不使用软删除。
- 不允许重复关联。
- 发型软删除时应删除其关联记录。
- 标签被删除前必须确认不存在关联。
- 批量更新标签关系时应使用事务。

# 八、Laravel Model 关系

public function parent()

# 十一、Migration 创建顺序

建议顺序：

```text
1. create_hairstyle_categories_table
2. create_hairstyle_tags_table
3. create_hairstyles_table
4. create_hairstyle_tag_relations_table
```

说明：

- 虽然不创建物理外键，仍按逻辑依赖顺序创建。
- `media_files` 应在发型模块前完成。
- 如果 `media_files` 尚未创建，不影响 Migration 执行，但对应 Model 关系需后续补齐。

# 十三、事务要求

以下操作必须使用数据库事务：

- 新增发型并保存标签关系
- 编辑发型并同步标签关系
- 删除发型并清理标签关联
- 批量移动发型分类
- 批量修改发型标签

示例：

```php
DB::transaction(function () use ($data, $tagIds) {
    $hairstyle = Hairstyle::create($data);
    $hairstyle->tags()->sync($tagIds);
});
```

# 十四、删除策略

## 14.1 发型分类

- 使用软删除。
- 存在子分类时禁止删除。
- 存在未删除发型时禁止删除。
- 恢复分类时不自动恢复子分类。

## 14.2 发型

- 使用软删除。
- 删除时清理 `hairstyle_tag_relations`。
- 不删除 `media_files`。
- 恢复发型后，标签关系不会自动恢复，需要业务层决定是否重建。

## 14.3 标签

- 不使用软删除。
- 存在关联时禁止删除。
- 可通过 `status = 0` 禁用。

## 14.4 标签关联

- 直接物理删除。
- 不保留历史关联记录。

# 十五、性能与查询规则

- 发型列表必须预加载分类和封面媒体。
- 标签仅在需要时预加载。
- 列表页禁止一次加载完整正文和 AI Prompt。
- 后台标签引用次数应使用聚合查询或 `withCount`。
- 禁止在循环中逐条查询分类、封面或标签。
- 前台列表查询应限制返回字段。
- 大批量导入时使用分批写入。
- `face_shape` 和 `suitable_scene` 不用于高频复杂 SQL 查询。

# 十七、Cursor 开发约束

Cursor 开发本模块时必须：

1. 阅读本文档及项目 `.cursor/rules`。
2. 检查是否已有同名 Migration、Model、Enum、Controller。
3. 不得自行修改字段名、字段类型、默认值和索引。
4. 不创建数据库物理外键。
5. 状态字段必须使用 PHP Enum 或统一常量。
6. 业务逻辑不得写入 Dcat Controller。
7. 标签同步、删除检查等逻辑放入 Service。
8. 生成 Migration、Model、Enum、Service、Dcat Admin 页面和 Seeder。
9. 不修改无关模块。
10. 完成后输出文件清单、执行命令和风险点。

# 十九、设计结论

HairHub V1.0 发型模块采用：

```text
分类主表
+
发型主表
+
标签主表
+
多对多关联表
```

该结构能够满足：

- 发型资产管理
- 发型分类展示
- 标签筛选
- AI 换发型目标选择
- SEO 页面建设
- Dcat Admin 后台运营
- 后续推荐系统扩展

V1.0 优先保证结构清晰、查询稳定和开发效率，不引入过多属性表和复杂关系表。
