# 一、模块目标

内容模块用于管理 HairHub 的核心内容资产，包括：

- 文章分类、文章标签
- 网站文章（含文章正文媒体、文章与发型/发色关联）
- 视频教程
- 微信公众号文章同步记录（仅数据结构预留，本阶段不接真实接口）

V1.0 第一阶段已实现以下数据表：

```text
article_categories
article_tags
articles
article_tag_relations
article_media
article_hairstyle_relations
article_hair_color_relations
videos
wechat_articles
```

`topics`（专题）表本阶段**未创建**，仅在本文档十三章保留设计参考，留待后续阶段实现（详见二十二、V1.0 暂不设计）。

# 二、数据关系

```text
article_categories
        │
        │ 1:N
        ▼
     articles ── N:N ── article_tags
        │  │
        │  │ N:N（article_hairstyle_relations）
        │  ▼
        │ hairstyles
        │
        │ N:N（article_hair_color_relations）
        ▼
    hair_colors

     articles
        │ 1:N
        ▼
  article_media ── N:1 ── media_files

     articles
        │ 1:0..1
        ▼
 wechat_articles


media_files
   ▲     ▲     ▲
   │     │     │
articles videos article_media
```

关系说明：

- 一个文章分类可以包含多篇文章，最多支持两级分类。
- 一篇文章只能归属一个主分类（`category_id`，默认 0 表示未分类，仅发布时强制要求非 0）。
- 一篇文章可以关联多个标签（`article_tags`，通过 `article_tag_relations`）。
- 一篇文章可以关联多个已有发型（`hairstyles`，通过 `article_hairstyle_relations`）、多个已有发色（`hair_colors`，通过 `article_hair_color_relations`）。
- 一篇文章可以关联多条正文图片/图集/附件媒体记录（`article_media`），但文章封面主逻辑始终使用 `articles.cover_media_id` / `articles.wechat_cover_media_id`，不重复放入 `article_media`。
- 一篇文章最多对应一条微信公众号同步记录（`wechat_articles`）。
- 文章、视频的封面/正文媒体通过 `media_files` 逻辑关联。
- 不创建数据库物理外键，所有关联关系由 Model + Service + 事务 + 索引保证一致性。

# 三、统一设计约定

## 3.1 基础规范

- 存储引擎：`InnoDB`
- 字符集：`utf8mb4`
- 主键：`BIGINT UNSIGNED AUTO_INCREMENT`
- 不创建数据库物理外键
- 所有逻辑关联字段必须建立索引
- 状态字段使用 `TINYINT UNSIGNED`
- 状态值由 PHP Enum 统一管理，Enum 均提供 `label()` / `options()` / `color()` / `values()` / `isValid()`
- 文章、视频、分类使用软删除；`article_tags` 与三张 N:N 关联表、`article_media`、`wechat_articles` 不使用软删除
- 内容正文使用 `LONGTEXT`
- 网站内容与公众号内容分开保存（`content` / `wechat_content` 互不覆盖）

## 3.2 排序规则

后台默认排序：

```text
sort DESC, id DESC
```

前台内容列表默认排序：

```text
published_at DESC, id DESC
```

说明：

- `sort` 用于运营置顶/排序。
- `published_at` 用于内容发布时间排序。
- `id` 保证相同时间或排序值下结果稳定。

## 3.3 内容生命周期状态（ContentStatus）

`articles.status`、`videos.status` 统一使用四状态生命周期，取代 1.0.0 版本中的
`draft / published / disabled` 三状态设计：

```text
0 = draft           草稿
1 = pending_review  待审核
2 = published       已发布
3 = offline         已下线
```

对应 PHP Enum（`App\Enums\Content\ContentStatus`）：

```php
enum ContentStatus: int
{
    case Draft = 0;
    case PendingReview = 1;
    case Published = 2;
    case Offline = 3;
}
```

合法状态流转（由 `ContentStatus::canTransitionTo()` 统一维护，Service 层不得绕过）：

```text
draft           -> pending_review
pending_review  -> draft            （审核打回）
pending_review  -> published        （审核通过）
published       -> offline          （下线）
offline         -> published        （重新上线）
```

说明：

- `draft`：草稿，仅后台可见。
- `pending_review`：待审核，已提交但未通过审核。
- `published`：已发布，满足前台展示条件时对外可见。
- `offline`：已下线，曾发布过，现手动下线；下线不清空 `published_at` 与审核信息，保留历史发布记录。
- 前台可见性判断（`Article::isVisibleOnFrontend()` / `Video::isVisibleOnFrontend()`）：
  `status = published` 且 `published_at` 不为空且 `published_at <= 当前时间` 且未被软删除。

## 3.4 其它内容相关 Enum

| Enum | 命名空间 | 取值 | 说明 |
|---|---|---|---|
| ContentFormat | `App\Enums\Content\ContentFormat` | 1=markdown，2=html | `articles.content_format` |
| ArticleMediaType | `App\Enums\Article\ArticleMediaType` | 1=content_image，2=gallery，3=attachment | `article_media.media_type`，取值从 1 开始（0 保留给“未设置”语义，本枚举不使用 0） |
| VideoSource | `App\Enums\Video\VideoSource` | 0=local，1=wechat_channels，2=douyin，3=kuaishou，4=bilibili，5=youtube，6=other | `videos.source` |
| WechatSyncStatus | `App\Enums\Wechat\WechatSyncStatus` | 0=pending，1=syncing，2=success，3=failed | `wechat_articles.sync_status` |
| WechatPublishStatus | `App\Enums\Wechat\WechatPublishStatus` | 0=unpublished，1=publishing，2=published，3=publish_failed | `wechat_articles.publish_status` |
| CommonStatus（复用） | `App\Enums\Common\CommonStatus` | 0=disabled，1=enabled | `article_categories.status`、`article_tags.status` 复用项目已有通用启用状态枚举，不单独定义 |

# 四、article_categories 文章分类表

## 4.1 表用途

管理文章分类，支持一级和二级分类（与发型分类、发色分类保持同样的两级分类设计）。

## 4.2 字段结构

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|---|---|---:|---:|---|
| id | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| parent_id | BIGINT UNSIGNED | 否 | 0 | 父分类 ID，0 表示顶级分类 |
| name | VARCHAR(100) | 否 | 无 | 分类名称 |
| name_en | VARCHAR(150) | 否 | `''` | 英文名称预留 |
| slug | VARCHAR(150) | 否 | 无 | SEO URL 标识 |
| description | VARCHAR(500) | 是 | NULL | 分类简介 |
| cover_media_id | BIGINT UNSIGNED | 否 | 0 | 分类封面媒体 ID |
| status | TINYINT UNSIGNED | 否 | 1 | 状态，对应 CommonStatus |
| sort | INT UNSIGNED | 否 | 0 | 排序值 |
| created_at | TIMESTAMP | 是 | NULL | 创建时间 |
| updated_at | TIMESTAMP | 是 | NULL | 更新时间 |
| deleted_at | TIMESTAMP | 是 | NULL | 软删除时间 |

## 4.3 索引设计

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_slug` (`slug`),
KEY `idx_parent_status_sort` (`parent_id`, `status`, `sort`),
KEY `idx_cover_media_id` (`cover_media_id`),
KEY `idx_deleted_at` (`deleted_at`)
```

## 4.4 业务规则（`App\Services\Content\ArticleCategoryService`）

- 顶级分类的 `parent_id = 0`。
- 不允许父级分类指向自身，也不允许指向自身的子分类。
- 最多支持两级分类，不能选择二级分类作为父级。
- 删除前必须检查未删除子分类和未删除文章引用，存在引用时拒绝删除。
- 删除仅执行软删除。
- 恢复分类时不自动恢复子分类，仅恢复目标分类自身；恢复前校验父分类（若非顶级）仍存在且未删除，以及 slug 是否冲突。
- 分类被禁用（`status = disabled`）只影响前台展示，不影响文章归属关系；文章发布时才强制要求分类必须启用。

# 五、article_tags 文章标签表

## 5.1 表用途

管理文章标签，供文章通过多对多关联进行内容聚合和检索（参照 `hairstyle_tags` 的成熟设计）。

## 5.2 字段结构

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|---|---|---:|---:|---|
| id | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| name | VARCHAR(100) | 否 | 无 | 标签名称 |
| slug | VARCHAR(150) | 否 | 无 | SEO URL 标识 |
| description | VARCHAR(500) | 否 | `''` | 标签说明 |
| status | TINYINT UNSIGNED | 否 | 1 | 状态，对应 CommonStatus |
| sort | INT UNSIGNED | 否 | 0 | 排序值 |
| created_at | TIMESTAMP | 是 | NULL | 创建时间 |
| updated_at | TIMESTAMP | 是 | NULL | 更新时间 |

`article_tags` **不使用 SoftDeletes**，与 `hairstyle_tags` 保持一致（标签体量小、删除前已强制检查引用，物理删除不会造成数据孤岛）。

## 5.3 索引设计

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_slug` (`slug`),
KEY `idx_status_sort` (`status`, `sort`)
```

## 5.4 业务规则（`App\Services\Content\ArticleTagService`）

- `slug` 必须唯一。
- `status` 必须是 CommonStatus 合法取值。
- 删除前检查 `article_tag_relations` 是否仍引用该标签，存在引用时拒绝删除（物理删除）。
- 文章与标签的同步（`syncTagsForArticle()`）：先校验全部 `tag_id` 均存在，再增量对比新增/移除，不整体替换导致中间态；已存在的关联不会被重复写入或重置 `created_at`。

## 6.3 索引设计

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_slug` (`slug`),
KEY `idx_category_status_published` (`category_id`, `status`, `published_at`),
KEY `idx_status_top_published` (`status`, `is_top`, `published_at`),
KEY `idx_status_recommended_sort` (`status`, `is_recommended`, `sort`),
KEY `idx_cover_media_id` (`cover_media_id`),
KEY `idx_wechat_cover_media_id` (`wechat_cover_media_id`),
KEY `idx_published_at` (`published_at`),
KEY `idx_deleted_at` (`deleted_at`)
```

## 6.4 业务规则（`App\Services\Content\ArticleService`）

创建 / 更新（草稿态）：

- 新建文章 `status` 始终为 `draft`，不接受外部传入的 `status`（唯一状态写入入口是 `changeStatus()`）。
- `category_id` 非 0 时必须指向存在且未删除的分类，不要求分类已启用。
- `title` 不能为空；`slug` 必须非空且唯一（跨软删除记录校验）。
- `cover_media_id` / `wechat_cover_media_id` 非 0 时必须指向状态可用（`MediaStatus::Active`）的媒体。
- `content_format` 必须是 `ContentFormat` 合法取值。
- `view_count` / `like_count` 只能通过 `updateCounts()` 维护，不允许写入负数。

状态流转（`changeStatus()`）：

- 合法流转规则见 3.3 节，非法流转直接拒绝。
- 流转到 `pending_review`：清空上一轮审核信息，进入新的审核周期。
- 流转到 `draft`（审核打回）：记录 `reviewed_by` / `reviewed_at` / `review_remark`。
- 流转到 `published`：必须满足全部发布前置条件（见下），并记录审核信息、写入 `published_at`。
- 流转到 `offline`：不清空 `published_at` 与审核信息，保留历史发布记录。
- 任意流转成功后都会确保存在一条 `wechat_articles` 预留记录。

发布前置条件（`assertPublishable()`）：

- 分类存在、未删除且状态启用。
- 标题非空、slug 非空、正文非空。
- 封面媒体存在且状态可用。
- 已关联的发型 / 发色关联，其对应的发型 / 发色当前仍必须存在、未删除且状态启用（防止关联建立后目标被软删除/禁用产生脏数据）。
- `published_at` 非空：取显式传入值，或文章已有的 `published_at`（例如草稿阶段已预先排期），两者都为空则拒绝——不会静默填充为当前时间。

前台可见性：`status = published` 且 `published_at` 不为空且 `published_at <= now()` 且未被软删除。

删除 / 恢复：

- 删除仅执行软删除，不删除 `article_media` / `article_tag_relations` / `article_hairstyle_relations` / `article_hair_color_relations` / `wechat_articles`。
- 恢复前重新校验所属分类仍存在未删除，并检查 slug 是否冲突。

# 七、article_tag_relations 文章标签关联表

## 7.1 表用途

文章与标签的多对多中间表。

## 7.2 字段结构

| 字段 | 类型 | 是否为空 | 默认值 | 说明 |
|---|---|---:|---:|---|
| id | BIGINT UNSIGNED | 否 | 自增 | 主键 |
| article_id | BIGINT UNSIGNED | 否 | 无 | 文章 ID |
| tag_id | BIGINT UNSIGNED | 否 | 无 | 标签 ID |

不包含 `updated_at`（与 `hairstyle_tag_relations` 保持一致，关联关系本身没有“更新”语义）。

## 7.3 索引设计

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_article_tag` (`article_id`, `tag_id`),

```

## 7.4 业务规则

- 唯一索引 + Service 层同步前置校验双重保证不产生重复关联。
- `ArticleTagService::syncTagsForArticle()` 直接操作本表模型完成增量同步（新增走 `create()`，移除走 `delete()`），不使用 `BelongsToMany::sync()` 批量写入 pivot 属性，避免把已存在关联的 `created_at` 误重置为当前时间。

# 八、article_media 文章媒体关联表

## 8.1 表用途

记录文章正文图片、图集、附件。文章封面主逻辑固定使用 `articles.cover_media_id` /
`articles.wechat_cover_media_id`，不复用本表。

| media_type | TINYINT UNSIGNED | 否 | 无 | 用途，对应 ArticleMediaType |
| alt_text | VARCHAR(255) | 否 | `''` | 图片 Alt 文本（图片 SEO） |
| caption | VARCHAR(500) | 否 | `''` | 图片说明 |
| sort | INT UNSIGNED | 否 | 0 | 排序值 |
| created_at | TIMESTAMP | 是 | NULL | 创建时间 |
| updated_at | TIMESTAMP | 是 | NULL | 更新时间 |

## 8.3 索引设计

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_article_media_type` (`article_id`, `media_id`, `media_type`),
KEY `idx_article_type_sort` (`article_id`, `media_type`, `sort`),
KEY `idx_media_id` (`media_id`)
```

## 8.4 业务规则（`App\Services\Content\ArticleMediaService`）

- 只允许关联状态可用（`MediaStatus::Active`）的媒体文件。
- `ArticleMediaType::ContentImage` / `Gallery` 要求关联的媒体文件类型必须是 `MediaFileType::Image`（图片），`Attachment` 不做类型限制。
- 同一文章下相同 `media_id + media_type` 不允许重复关联（数据库唯一索引 + Service 层前置校验双重保证）。
- 提供 `attachMedia` / `detachMedia` / `updateRelation` / `syncMedia`（按用途整体替换并重排 `sort`）/ `reorderMedia`。
- 解除关联只删除 `article_media` 记录，不删除 `media_files` 原始记录。

# 九、article_hairstyle_relations 文章发型关联表

## 9.1 表用途

## 9.4 业务规则（`ArticleService::syncHairstyles()`）

- 只允许关联存在、未删除且状态为启用（`HairstyleStatus::Enabled`）的发型。
- 增量同步：对比当前关联与目标列表，移除多余关联、新增缺失关联、更新排序，未变化的关联不做任何写入（不重置 `created_at`）。
- 删除关联不会删除发型本身。
- 文章发布前会重新校验现有关联的发型是否仍然存在且启用，防止关联建立后发型被软删除/禁用产生脏数据。

# 二十、删除策略

## 20.1 文章分类

- 使用软删除；存在子分类或未删除文章时禁止删除；恢复分类时不自动恢复子分类。

## 20.2 文章标签

- **不使用软删除**（物理删除）；删除前必须检查 `article_tag_relations` 引用，存在引用时拒绝删除。

## 20.3 文章

- 使用软删除；不删除媒体资源、标签关联、发型/发色关联、微信同步记录；恢复前检查分类是否仍存在未删除，以及 slug 是否冲突。

## 20.4 文章媒体关联 / 文章发型关联 / 文章发色关联

- 均为中间表记录，直接物理删除关联行；删除关联绝不删除被关联的 `media_files` / `hairstyles` / `hair_colors` 原始记录。

## 20.5 视频

- 使用软删除；不删除封面和视频媒体；不删除外部平台资源。

## 20.6 微信同步记录

- 不使用软删除；原则上不允许后台删除；文章软删除/恢复均不影响该记录。

# 二十五、设计结论

HairHub V1.0 内容模块第一阶段采用：

```text
文章分类 + 文章标签
+
文章主表 + 文章标签关联 + 文章媒体关联 + 文章发型关联 + 文章发色关联
+
视频主表
+
微信公众号同步表（数据结构预留）
```

该结构在保持“不创建物理外键、Laravel 原生优先、简单优先”的项目总原则下，实现了：

- 网站内容创建、审核、发布全生命周期管理（四状态 `ContentStatus`）。
- 文章与已有发型/发色内容资产的双向内容聚合能力，为 SEO 内链和推荐打基础。
- 文章正文媒体（图片/图集/附件）的规范化管理，支持图片 SEO（`alt_text`）。
- 微信生态转化所需的数据结构预留，不提前引入真实接口依赖和复杂度。

本阶段不涉及 Dcat Admin 页面、Seeder、真实微信接口、专题（topics）、评论/收藏/明细类高成本功能，
遵循“先上线，再积累，再优化”的项目长期原则，为后续阶段的 Admin 页面开发和公众号同步 Job 开发
预留清晰、稳定的数据结构和业务规则基础。
