# HairHub V1.0 媒体资源模块 MySQL 表结构详细设计

> Version: 1.0.0  
> 适用项目：HairHub 发型中心  
> 技术栈：Laravel 10 + Dcat Admin + MySQL 8.0+  
> 文档路径：`/docs/v1.0/database/05-媒体资源模块.md`

---

# 一、模块目标

媒体资源模块用于统一管理 HairHub 中的图片、视频及其元数据，包括：

- 用户上传图片
- AI 输入图片
- AI 生成结果图片
- 发型封面
- 发色封面
- 文章封面
- 正文图片
- 视频封面
- 本地视频
- 专题封面
- 临时文件
- 缩略图和衍生图

V1.0 重点解决：

- 文件统一入库
- 存储驱动抽象
- 路径与访问地址管理
- 文件类型和 MIME 记录
- 图片宽高和文件大小记录
- 缩略图管理
- 来源追踪
- 文件去重
- 临时文件过期
- 安全删除与清理

V1.0 涉及以下数据表：

```text
media_files
```

# 二、模块边界

媒体资源模块负责：

- 保存媒体元数据
- 统一文件路径
- 记录文件来源
- 记录缩略图和尺寸
- 记录存储位置
- 记录过期时间
- 支持文件去重和清理

媒体资源模块不负责：

- 业务内容本身
- CDN 配置管理
- 上传鉴权策略
- 视频转码流程
- 图片审核流程
- 文件实际二进制内容
- 对象存储密钥
- 复杂版权授权管理

以上能力分别由：

```text
业务模块
Laravel Filesystem
对象存储
队列任务
内容安全服务
环境变量与配置中心
```

负责。

# 三、数据关系

```text
media_files
   ▲
   ├── hairstyles.cover_media_id
   ├── hair_colors.cover_media_id
   ├── articles.cover_media_id
   ├── articles.wechat_cover_media_id
   ├── videos.cover_media_id
   ├── videos.video_media_id
   ├── topics.cover_media_id
   ├── ai_tasks.input_media_id
   └── ai_tasks.result_media_id
```

说明：

- 业务表通过逻辑 ID 关联媒体。
- 不创建数据库物理外键。
- 一个媒体文件可以被多个业务对象复用。
- 业务数据删除时不得直接删除共享媒体。

# 四、统一设计约定

## 4.1 基础规范

- 存储引擎：`InnoDB`
- 字符集：`utf8mb4`
- 主键：`BIGINT UNSIGNED AUTO_INCREMENT`
- 不创建数据库物理外键
- 逻辑关联字段必须建立索引
- 文件路径优先保存相对路径
- URL 仅作为缓存或兼容字段
- 不在数据库中保存二进制内容
- 文件名使用随机值或哈希值
- 原始文件名仅作展示和追踪
- 临时文件通过 `expired_at` 控制生命周期
- 媒体记录默认不使用软删除

## 4.2 存储驱动

建议字段 `storage` 保存：

```text
local
public
s3
oss
cos
r2
other
```

说明：

- 保存 Laravel Filesystem disk 名称。
- 不直接保存 Bucket 密钥。
- 业务代码通过 `Storage::disk($storage)` 访问文件。
- CDN 域名不写死在路径中。

## 4.3 路径规则

数据库优先保存：

```text
uploads/ai/2026/07/11/abc123.jpg
```

不建议只保存：

```text
https://cdn.example.com/uploads/ai/2026/07/11/abc123.jpg
```

原因：

- 便于切换域名。
- 便于切换 CDN。
- 便于多环境部署。
- 便于本地和对象存储统一。

# 六、字段详细说明

## 6.1 file_no

媒体业务编号，建议格式：

```text
MED202607110001
```

用途：

- 外部接口查询
- 日志追踪
- 避免暴露自增 ID

要求：

- 全局唯一
- 由 Service 统一生成

## 6.2 file_type

建议枚举：

```text
0 = unknown
1 = image
2 = video
3 = audio
4 = document
```

V1.0 主要使用 image 和 video。

## 6.3 path

规则：

- 必须保存相对路径。
- 不以 `/` 开头。
- 不包含域名。
- 不包含 `..`。
- 不允许用户直接控制完整路径。
- 必须经过统一上传 Service 生成。

示例：

```text
uploads/user/2026/07/11/abc123.jpg
uploads/ai/2026/07/11/def456.png
uploads/article/2026/07/11/ghi789.webp
```

## 6.4 url

`url` 作为兼容和缓存字段。

规则：

- 可为空字符串。
- 不作为唯一数据来源。
- 域名切换后可重新生成。
- 读取时优先根据 `storage + path` 动态生成。
- 不建议在业务代码中长期依赖数据库 URL。

## 6.5 original_name 与 filename

```text
original_name = 用户上传时文件名
filename = 实际保存文件名
```

规则：

- `original_name` 仅用于展示和追踪。
- `filename` 必须为随机值或哈希值。
- 禁止直接使用原始文件名保存。
- 保存前移除路径字符和危险字符。

## 6.6 extension 与 mime_type

示例：

```text
extension = jpg
mime_type = image/jpeg
```

规则：

- 扩展名和 MIME 必须同时校验。
- 禁止只根据扩展名判断文件类型。
- 服务端应重新检测 MIME。
- 扩展名统一保存小写。

## 6.7 size

单位：

```text
byte
```

规则：

- 使用 BIGINT UNSIGNED。
- 上传前后均需检查大小限制。
- 禁止使用 KB 或 MB 作为数据库单位。

## 6.8 width、height、duration

- 图片保存宽高。
- 视频保存宽高和时长。
- 无法识别时保存 0。
- 不为这些字段创建普通索引。

## 6.9 hash

使用：

```text
SHA-256
```

规则：

- 允许 NULL。
- 可用于文件去重。
- 不建议设置全局唯一索引，因为同一文件可能在不同业务生命周期中独立存在。
- 如启用强去重，可结合 `storage + hash` 查询。

## 6.10 thumbnail_path 与 thumbnail_url

用于保存默认缩略图。

规则：

- V1.0 只保存一张默认缩略图。
- 缩略图与原文件使用同一存储驱动。
- 没有缩略图时保存空字符串。
- 后续需要多尺寸时再增加独立衍生资源表。

## 6.11 source_type 与 source_id

用于追踪媒体来源。

建议来源类型：

```text
0 = unknown
1 = user_upload
2 = ai_input
3 = ai_result
4 = hairstyle
5 = hair_color
6 = article
7 = video
8 = topic
9 = admin_upload
```

说明：

- `source_id` 保存来源业务 ID。
- 来源尚未落库时允许 `source_id = 0`。
- 来源关系主要用于追踪，不替代业务表中的媒体 ID。

## 6.12 visibility

建议枚举：

```text
0 = private
1 = public
2 = protected
```

说明：

- private：仅内部使用。
- public：可公开访问。
- protected：需要签名或鉴权访问。

用户原图和 AI 输入图建议默认 private 或 protected。

## 6.13 status

建议枚举：

```text
0 = disabled
1 = active
2 = missing
3 = processing
```

说明：

- active：文件可正常使用。
- disabled：已禁用。
- missing：数据库记录存在但实际文件缺失。
- processing：正在生成缩略图或转码。

## 6.14 metadata

示例：

```json
{
  "exif_orientation": 1,
  "color_space": "sRGB",
  "codec": "h264",
  "bitrate": 1200000
}
```

规则：

- 保存弱查询扩展数据。
- 不保存敏感信息。
- 不保存核心字段副本。
- 不作为高频筛选条件。

## 6.15 expired_at

用途：

- 匿名用户临时上传
- AI 中间文件
- 临时生成结果
- 上传未完成文件

规则：

- NULL 表示不过期。
- 过期不代表立即删除。
- 清理任务应先检查业务引用。
- 过期后可禁止继续访问。

# 七、索引设计

```sql
PRIMARY KEY (`id`),
UNIQUE KEY `uk_file_no` (`file_no`),
UNIQUE KEY `uk_storage_path` (`storage`, `path`),
KEY `idx_hash` (`hash`),
KEY `idx_source_type_id` (`source_type`, `source_id`),
KEY `idx_type_status_created` (`file_type`, `status`, `created_at`),
KEY `idx_visibility_status` (`visibility`, `status`),
KEY `idx_expired_at` (`expired_at`)
```

说明：

- `storage + path` 必须唯一。
- `hash` 用于去重查询，但不强制唯一。
- 来源关系使用联合索引。
- 过期清理使用 `expired_at` 索引。
- 不为 URL、文件名和 MIME 建立普通索引。

- 目录层级保持稳定。
- 不同来源分目录，便于生命周期和权限管理。

# 十、文件格式建议

## 10.1 图片

V1.0 建议支持：

```text
jpg
jpeg
png
webp
```

可选支持：

```text
avif
```

限制：

- 用户上传原图可保留 jpg/png/webp。
- 前台展示优先生成 webp。
- AI 模型输入格式按模型要求转换。
- SVG 默认禁止用户上传，后台可信资源可单独放行。

## 10.2 视频

V1.0 建议支持：

```text
mp4
webm
mov
```

前台主格式建议：

```text
mp4 + H.264
```

## 10.3 MIME 校验

允许列表必须集中配置。

禁止：

- 仅按扩展名放行。
- 任意脚本文件。
- 可执行文件。
- 未知 MIME 直接公开访问。

# 十一、上传流程

标准流程：

```text
接收上传
↓
校验大小、MIME、扩展名
↓
生成随机文件名
↓
写入临时目录
↓
计算 SHA-256
↓
读取宽高、时长等元数据
↓
上传到目标存储
↓
创建 media_files 记录
↓
生成缩略图
↓
更新缩略图字段
```

要求：

- 数据库入库失败时清理已上传文件。
- 文件上传失败时不创建数据库记录。
- 涉及多个操作时通过 Service 统一处理。
- 不能在 Dcat Controller 中直接写上传逻辑。

---

# 十二、去重策略

V1.0 推荐弱去重：

```text
storage + hash + size
```

规则：

- 上传后计算 SHA-256。
- 查询是否存在相同文件。
- 业务可选择复用已有媒体记录。
- 用户私有上传默认不跨用户强制复用。
- AI 中间文件不强制去重。
- 公共素材可启用复用。

不建议：

- 仅按文件名去重。
- 仅按大小去重。
- 将 hash 设置为全局唯一。

---

# 十三、缩略图策略

V1.0 只保存一张默认缩略图：

```text
thumbnail_path
thumbnail_url
```

建议尺寸：

```text
300 × 300
```

或按比例最长边：

```text
480px
```

规则：

- 原图不覆盖。
- 保持宽高比。
- 图片缩略图优先使用 webp。
- 视频缩略图截取首个有效画面。
- 缩略图生成失败不影响原文件入库，但状态和错误应记录到日志。
- 多尺寸需求后续增加 `media_variants` 表。

# 十四、访问控制

## 14.1 public

适用于：

- 发型封面
- 发色封面
- 文章封面
- 公开视频
- 专题封面

可直接通过 CDN 或公开 URL 访问。

## 14.2 private

适用于：

- 用户原始照片
- AI 输入图片
- 内部模型中间文件
- 未发布内容

访问方式：

- 后端代理
- 临时签名 URL
- 鉴权接口

## 14.3 protected

适用于：

- AI 生成结果
- 需要登录后查看的资源
- 有有效期限制的下载

规则：

- 不直接暴露永久公开地址。
- URL 应设置有效期。
- 数据库只保存路径，不保存长期签名 URL。

# 十五、删除与清理策略

## 15.1 业务删除

删除文章、发型、发色等业务数据时：

- 不直接删除媒体文件。
- 不直接删除媒体记录。
- 先检查是否被其他业务引用。
- 由清理任务统一处理孤立媒体。

## 15.2 媒体删除

删除媒体前必须确认：

- 不被任何业务字段引用。
- 不被 AI 任务引用。
- 不被专题配置引用。
- 不属于需要保留的审计数据。

删除顺序：

```text
标记不可用
↓
检查引用
↓
删除缩略图
↓
删除原文件
↓
删除数据库记录
```

## 15.3 过期清理

定时任务查询：

```sql
WHERE expired_at IS NOT NULL
  AND expired_at < NOW()
  AND status = 1
```

清理前必须再次检查业务引用。

## 15.4 丢失文件

当数据库记录存在但文件不存在时：

```text
status = missing
```

后台应提供检测和修复入口。

# 十六、Laravel Model

## 16.1 MediaFile

建议关系不在媒体模型中大量反向声明，避免模型耦合过重。

可保留基础方法：

```php
public function getUrlAttribute($value): string
{
    if ($value !== '') {
        return $value;
    }

    return Storage::disk($this->storage)->url($this->path);
}
```

私有文件不应直接使用公开 `url()`，应通过 Service 生成临时地址。

## 16.2 casts

```php
protected $casts = [
    'file_type' => MediaFileType::class,
    'size' => 'integer',
    'width' => 'integer',
    'height' => 'integer',
    'duration' => 'integer',
    'source_type' => MediaSourceType::class,
    'visibility' => MediaVisibility::class,
    'status' => MediaStatus::class,
    'metadata' => 'array',
    'expired_at' => 'datetime',
];
```

不使用：

```text
SoftDeletes
```

# 十八、Service 设计要求

建议：

```text
MediaService
MediaUploadService

MediaCleanupService

```

## 18.1 MediaUploadService

负责：

- 上传校验
- 生成文件名
- 计算 hash
- 写入存储
- 创建数据库记录
- 读取媒体元数据

## 18.2 MediaUrlService

负责：

- 生成公开 URL
- 生成临时签名 URL
- 处理 CDN 域名
- 避免业务层直接拼接路径

## 18.3 ThumbnailService

负责：

- 图片缩略图
- 视频封面
- 格式转换
- 更新缩略图字段

## 18.4 MediaCleanupService

负责：

- 查询过期文件
- 检查业务引用
- 删除原文件和缩略图
- 处理丢失文件
- 输出清理报告

# 十九、Queue Job

建议：

```text
GenerateMediaThumbnailJob
CleanupExpiredMediaJob
DetectMissingMediaJob
```

- `GenerateMediaThumbnailJob`：异步生成缩略图。
- `CleanupExpiredMediaJob`：清理过期且无引用媒体。
- `DetectMissingMediaJob`：检测数据库与存储不一致。

大文件上传、视频元数据读取和缩略图生成应尽量异步执行。

# 二十二、Seeder 建议

V1.0 不建议 Seeder 写入真实媒体文件。

可选：

- 创建少量演示记录。
- 使用可访问的公共测试文件。
- 仅在本地或测试环境执行。

要求：

- 不写死生产域名。
- 不写入不存在的本地路径。
- 不写入真实用户图片。
- 不写入敏感文件。

# 二十三、性能规则

- 列表查询限制字段。
- 业务列表通过预加载获取媒体。
- 不在循环中逐条生成复杂签名 URL。
- 私有 URL 可短时缓存。
- 大量文件检测必须分批执行。
- 不对 `url` 做高频模糊搜索。
- hash 查询使用索引。
- 过期清理按 `expired_at` 分批处理。
- 大文件上传不占用长事务。

---

# 二十四、安全规则

- 服务端校验 MIME 和扩展名。
- 禁止路径穿越。
- 禁止用户控制 storage 名称。
- 禁止上传脚本和可执行文件。
- 私有文件不得直接暴露永久 URL。
- 用户原图不得默认公开。
- 上传文件名必须随机化。
- EXIF 中的敏感定位信息建议清理。
- 公开图片建议去除不必要 EXIF。
- 日志不得记录完整签名 URL。
- 对象存储密钥只放环境变量或安全配置。

# 二十六、Cursor 开发约束

Cursor 开发本模块时必须：

1. 阅读本文档和 `.cursor/rules`。
2. 检查是否已有同名 Migration、Model、Enum、Service、Job、Controller。
3. 不得自行修改字段、类型、默认值和索引。
4. 不创建数据库物理外键。
5. 路径必须保存相对路径。
6. 不在数据库保存二进制和 Base64。
7. 不把密钥和签名参数写入数据库。
8. 文件上传必须通过 Service。
9. Dcat Controller 不得直接处理存储逻辑。
10. 删除前必须检查业务引用。
11. 私有文件必须通过临时 URL 或鉴权接口访问。
12. MIME 与扩展名必须同时校验。
13. 缩略图生成使用 Queue Job。
14. 媒体记录不使用软删除。
15. 不修改无关模块。
16. 完成后输出文件清单、执行命令和风险点。

# 二十八、设计结论

HairHub V1.0 媒体资源模块采用：

```text
单一 media_files 核心表
+
Laravel Filesystem
+
对象存储或本地存储
+
缩略图与清理 Queue Job
```

该结构能够满足：

- 用户上传
- AI 输入和结果
- 发型、发色和内容封面
- 视频资源
- 存储驱动切换
- 文件去重
- 私有访问
- 缩略图
- 过期清理
- 后台排查

V1.0 优先保证路径统一、访问安全、生命周期可控和业务复用，不提前引入多尺寸衍生表、引用表与复杂转码系统。
